# H0.7+ Design Notes (2026-08-19)

Durable intent for H0.7 and beyond. Captures the design direction,
recovery chain, overnight target, and the cache-lane findings that
constrain H0.7's search axes. PLAN.md stays the locked milestone list;
this file holds the rationale and the gates that must hold before any
new optimization is trusted.

## Direction: Qwen-as-research-agent

Qwen 3.8 is the agent that proposes optimizations for the entire stack
underneath itself (workload -> llama.cpp config -> KV/cache ->
batching/speculation -> quant -> backend -> GPU kernels -> drivers ->
host environment). Hyperloom is the controlled laboratory and judge,
never an editor of production. The loop:

```
Qwen 3.8 running on the machine
  -> profiles its own workload
  -> finds bottleneck
  -> researches possible improvement
  -> proposes ONE change
  -> Hyperloom builds isolated candidate
  -> same Qwen workload runs again
  -> correctness + speed + latency + power + coding quality measured
  -> KEEP / REJECT (against statistical baseline)
  -> Qwen sees evidence, proposes next experiment
```

Search can descend progressively: workload -> llama.cpp config ->
cache/KV/context -> batching/speculation/MTP -> quant + tensor
placement -> Vulkan/HIP backend -> custom gfx1100 GPU kernels ->
Mesa/RADV/ROCm -> amdgpu + Linux environment -> PCIe/OCuLink + host
scheduling + power. End goal is correct coding work per wall-clock
hour, not raw tok/s.

## Recovery chain (rollback layers)

Five independent rollback layers so one bad experiment cannot brick
the working stack:

1. **Git** - every experiment starts from a pinned known-good SHA.
   Qwen edits an isolated branch/worktree. Bad candidate -> discard
   the worktree/commit. Known-good source stays untouched.
2. **Production binary stays separate** - candidate binary is built
   separately and launched on the experiment port (18179). It does
   not overwrite the production llama-server binary. Crash/OOM/wrong
   output -> kill candidate, return to known-good.
3. **Hyperloom RestoreTrap** - before touching anything it captures
   the pre-state (services, listeners, GPU ownership, PIDs/PGIDs,
   health). RestoreTrap wraps the dangerous section and on
   success/failure/timeout/signal: kills the candidate process tree,
   restarts services it stopped, verifies ports, resolves restarted
   service PIDs, checks GPU ownership, compares post-state against
   pre-state. A benchmark can succeed and still be marked FAIL if
   restoration failed.
4. **Systemd** - the stable Qwen service configuration is the
   known-good launch path. Hyperloom drains it temporarily for
   exclusive experiments and restores it. A candidate never becomes
   the production systemd service merely because it benchmarked
   faster. Promotion to production is a separate human-approved act.
5. **Experiment DB** - every run records identities (Hyperloom SHA,
   llama.cpp SHA, binary SHA, GGUF SHA, build flags, runtime flags,
   ROCm/Mesa/kernel versions, hardware identity, measurements,
   outcome). After a bad experiment you know exactly which
   configuration was last proven good.

The model itself is immutable. The Qwen GGUF is SHA-verified.
Optimization experiments must not modify the canonical model file.

When GPU kernels land: stable kernel implementation + candidate
kernel, compile separately, correctness tests, benchmark, FAIL ->
discard, PASS -> retain. Old implementation is not deleted; ideally
runtime/build switches make the known-good kernel selectable until
the new one passes every gate.

## Overnight autonomous target

Yes, this is the intended operating mode, but not in its current
state. The prerequisites are:

1. Real N=5 unchanged baseline on the RX 7900 XTX (NOT yet run; the
   H0.6.4 lifecycle is closed and verified, the measurement is
   wired, but the run itself is blocked on an exclusive-XTX window).
2. 20-job coding baseline (success rate, first-pass, pytest, lint,
   retries, tokens, wall-clock) to make "coding work/hour" a real
   metric.
3. H0.7 structured for unattended: maximum experiment duration,
   maximum consecutive failures, candidate isolation, exclusive-XTX
   check before every measurement, temperature/power/VRAM/load
   gates, candidate process-tree cleanup after every run,
   restoration verification after every run, correctness failures =
   immediate REJECT, no autonomous kernel/firmware/boot changes,
   disk-space and DB/log-size limits, a global overnight deadline,
   known-good systemd service restored before the supervisor exits,
   and a self-throttling loop that detects when hypotheses converge
   on the same kernel without gain and switches search area or
   terminates.

Once those hold, an overnight run looks like:

```
00:30  verify exclusive XTX + host health
  ->   load known-good baseline
  ->   Qwen reads previous experiment evidence
  ->   propose ONE hypothesis
  ->   isolated worktree + candidate build
  ->   correctness gate
  ->   benchmark candidate
  ->   KEEP / REJECT
  ->   write experiment DB + logs
  ->   restore known-good machine state
  ->   next hypothesis
07:00  stop search
  ->   restore stable production service
  ->   produce morning report
```

The morning report should look something like:

```
Qwen baseline: 29.0 tok/s, coding work/hour: X
N experiments attempted
N rejected
N invalid
N retained
Best retained: +6.8% prompt throughput, -11% TTFT, +4.3% coding
work/hour, same correctness, same model SHA.
Machine restored: PASS. Production healthy: PASS.
```

You decide whether the retained candidate gets promoted.

## Cache-lane findings (constrain H0.7's search axes)

The other agent's pollution-oracle experiments on llama.cpp's hybrid
checkpoint cache (ctxcp) concluded:

- **Checkpoint rollback bug: NO.** With LCP 20,426 llama.cpp restored
  the best valid checkpoint at 5,870 instead of resetting to zero;
  the implementation is correct.
- **Single-slot pollution: YES, dominant.** With `-np 1`, B becomes
  the slot's active prefix, A1's checkpoints beyond B's tiny LCP are
  invalidated, and A2 consequently has no useful A-state to
  restore. This produces ~30 s re-prefill on 17.5K tokens after one
  unrelated 58-token request.
- **Coarse checkpoint density: YES, secondary.** Checkpoints sit at
  user-message boundaries; finer placement would reduce wasted state
  but does not fix the dominant pollution mechanism.
- **Tiny-checkpoint warning noise: YES, secondary.** A small guard
  (`task->n_tokens() >= checkpoint_min_step`) suppresses checkpoint
  creation for prompts shorter than the step (256 here). Verified
  safe: `task->n_tokens()` is the full tokenized prompt, never a
  cached prefix delta, so the guard only short-circuits genuinely
  short prompts and does not change long-context coverage.

Implication for H0.7: do **not** spend search budget on
`ctxcp`/`cms`/checkpoint-creation tuning. The dominant cost is
single-slot reuse policy. Higher-ROI fixes, in order from least
invasive:

1. Traffic isolation/routing - dedicate the workhorse slot to
   OpenCode; health probes must not submit inference prompts to it.
2. Separate inference lane - tiny/Tier-2 requests go to another
   server/process/port.
3. `-np > 1` with affinity - only useful if session/request routing
   reliably sends the long conversation back to its preserved slot.
4. Server-level slot affinity/reservation - preserve a slot for a
   session ID rather than letting arbitrary traffic evict it.
5. Persistent multi-prefix/checkpoint cache - larger architectural
   change allowing A checkpoints to survive B slot reuse.

For Hyperloom's objective (correct coding work/hour), options 1 or
2 are likely higher ROI than modifying checkpoint creation. H0.7
config search should treat routing/affinity as a first-class search
axis when the harness can express it; pure llama.cpp-side changes
are a secondary lane.

## Hard limits for any future unattended run

- 8-12 minute maximum per experiment.
- 3 consecutive failures -> abort the night.
- Candidates in isolated worktrees + experiment ports only.
- No production overwrite.
- Exclusive-XTX check before every measurement.
- Temperature / power / VRAM / load gates.
- Candidate process-tree cleanup after every run.
- Restoration verification after every run.
- Correctness failures = immediate REJECT.
- No autonomous kernel / firmware / boot changes (until H5 is
  authorized AND disaster-recovery tier is in place).
- Disk-space and DB/log-size limits.
- Global overnight deadline; known-good systemd service restored
  before supervisor exits.
