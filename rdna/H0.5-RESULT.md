## How the evaluator is invoked

```bash
cd /home/homelabserver/hyperloom-rdna
# Baseline: 5 measurements on the pinned identity, recorded in the DB.
python -m rdna.h05.cli baseline --label prod-pin-2026-08-17 \
    --port 18180 --repeat 5
# Candidate: same but as the candidate set (after a build / recipe change).
python -m rdna.h05.cli candidate --label prod-pin-2026-08-17 \
    --port 18180 --repeat 5
# Decide: compare baseline vs candidate across all six metrics, record
# the decision in the DB.
python -m rdna.h05.cli decide --label prod-pin-2026-08-17
# Show one experiment's identity + per-iteration measurements.
python -m rdna.h05.cli show --label prod-pin-2026-08-17
```

The evaluator talks to the bypass-scriptable executor directly
(`hyperloom.orchestrator.actions.executors.bypass_runner._run_scriptable_benchmark`)
— the same seam the H0.0 smoke driver used — so the gating logic is
observable and deterministic regardless of the Hyperloom CLI's PRELUDE
behaviour (H0-GAP-001).

## Decision thresholds (frozen)

- **PROMOTE**: candidate improvement > `max(2σ of baseline, +3 %)` on the
  primary metric (`output_throughput` tok/s for higher-is-better;
  `mean_tpot_ms` / `mean_e2el_ms` / `prompt_eval_ms` for lower-is-better).
- **APPROVE**: candidate improvement > `+1 %` AND <= promote floor
  (the evaluator learns the recipe works, does not yet promote it).
- **RETAIN**: otherwise (no improvement, or candidate regressed).
- **INCONCLUSIVE**: empty samples (caller must re-run).

A/B/A interleaving (`compare_aba`) is provided; H0.5 first pass does not
enforce it as a hard gate (the agent loop that drives A/B/A belongs to
H0.7's config-search work).

## What is NOT in H0.5 first pass

These are deliberately deferred; H0.5's first milestone is the
evaluator, not the optimizer.

1. **Tiered gate enforcement** (fast-perf → perf matrix → product gate).
   The compare() decision is per-metric; the CLI's `decide` aggregates
   to PROMOTE/APPROVE/RETAIN but does not yet have a product metric
   ("correct work per wall-hour") that outranks raw tok/s. This belongs
   to the H0.5 second pass when a coding-job product workload is wired
   in.
2. **Build-from-SHA step.** The identity block records the binary SHA
   but does not rebuild llama.cpp from the pinned source SHA. The
   production pin (c6903632b) is assumed-built; an H0.5 second-pass
   build step is straightforward (cmake -B build && cmake --build
   build) and was deferred because the binary is already present and
   the fork is itself a deliverable.
3. **20-job coding-job product baseline.** Requires a coding harness
   that does not exist on this host today; out of scope for H0.5
   first pass.
4. **Tiered gates fast-perf → perf matrix → product gate.** Same as #1.
5. **A/B/A interleaving as a hard PROMOTE gate.** Provided as
   `compare_aba`; the CLI's `decide` does not yet enforce it. Will be
   promoted to a hard gate when H0.7's agent loop drives A/B/A
   experiments.

## Notes for H0.5 second pass / H0.6 / H0.7

- The gate is what makes the evaluator trustworthy. The current gate is
  conservative (GGUF size as lower bound for VRAM, 10 % minimum free).
  An H0.5 second pass can tighten the bound by querying the model's
  actual peak VRAM via a warmup probe (load-and-measure).
- The decision rule treats every metric independently. A second pass
  should add a weighted product metric ("correct work per wall-hour")
  that outranks raw tok/s; until then the user-facing decision is
  per-metric, which is honest but noisy.
- The CLI has a BLOCKED-experiment path: when the gate fails the
  experiment row + a `blocked=True` run row are written so the operator
  sees the attempt in `list`. This is the right behaviour (auditability)
  and should be preserved across the H0.5 → H0.6 transition.
- The fork's `feature/rdna-llamacpp` branch has 8 commits (H0.0 +
  H0.0+ closure + H0.5 framework); all pushed to
  github.com/richardoros/Hyperloom.
