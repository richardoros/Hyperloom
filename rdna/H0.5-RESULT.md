## Decision thresholds (frozen)

- **PROMOTE**: candidate improvement > `max(2σ of baseline, +3 %)` on the
  primary metric (`output_throughput` tok/s for higher-is-better;
  `mean_tpot_ms` / `mean_e2el_ms` / `prompt_eval_ms` for lower-is-better).
  **Requires `allow_promote=True`**, which only `compare_aba()` (the
  A/B/A confirmation path) sets today. The CLI's `decide` subcommand
  does NOT pass it, so PROMOTE is unreachable until A/B/A is wired into
  the agent loop and the product-quality gate exists.
- **APPROVE**: candidate improvement > `+1 %` AND <= promote floor
  (the evaluator learns the recipe works, does not yet promote it).
- **RETAIN**: otherwise (no improvement, or candidate regressed).
- **INCONCLUSIVE**: empty samples (caller must re-run).

Sigma-floor is now `abs((2σ)/median)` regardless of metric direction
(P0.3 fix). The pre-fix implementation returned a negative number for
`direction='lower'`, which collapsed the noise floor to the promote
floor for latency metrics.

Build-from-SHA provenance: `rdna.h05.build_provenance.verify_provenance()`
rebuilds the candidate from the pinned source SHA + build config into
an isolated evaluator-owned directory (e.g.
`rdna/h05_results/builds/<source-sha>/<build-config-hash>/`) and asserts
the resulting binary SHA-256 matches the observed identity block's
`binary_sha256`. The production build tree is never mutated.

## What is NOT in H0.5 first pass

These are deliberately deferred; H0.5's first milestone is the
evaluator, not the optimizer.

1. **A/B/A interleaving as a CLI subcommand.** `compare_aba` is
   implemented and unit-tested but the CLI does not expose it. The
   candidate/baseline/fresh-baseline interleaving protocol that drives
   A/B/A belongs to H0.7's agent loop.
2. **20-job coding-job product baseline.** Requires a coding harness
   that does not exist on this host today; out of scope for H0.5.
3. **Tiered gate enforcement** (fast-perf → perf matrix → product gate).
   The compare() decision is per-metric; the CLI's `decide` aggregates
   to APPROVE/RETAIN but does not yet have a product metric ("correct
   work per wall-hour") that outranks raw tok/s. This belongs to the
   H0.5 second pass when a coding-job product workload is wired in.
4. **Build-from-SHA step on the production checkout** (i.e. actually
   rebuilding the pinned llama.cpp from source as part of every
   `candidate` run). The build infrastructure is in place
   (`build_provenance.py`); wiring it into the CLI is deferred to H0.5
   second pass.
5. **Schema migration framework.** v1 → v2 was done with
   archive-and-create-fresh. A proper migration is deferred to H0.5
   second pass when the experiment DB is expected to outlive several
   revisions.
6. **Per-process PID-to-GPU UUID attribution.** The current gate
   attributes llama-server processes to "uses GPU layers or not" via
   command-line inspection (excluding CPU-only embedding servers).
   Mapping a specific PID to a specific GPU UUID is left for H0.6
   (which will own the exclusive-XTX lifecycle). The gate's
   `foreign_owners_on_gpu` parameter accepts a caller-supplied
   PID set for a future PID-to-UUID mapper; today the caller passes
   an empty set.

## H05-GAP-002 (carry into H0.6)

```text
H05-GAP-002:
build_provenance.build_candidate() always creates a fresh
'git worktree add --detach build_root/worktrees/<source_sha>'.
A second provenance build using the same SHA and same build_root
fails because the worktree path already exists.

Fix (deferred; do NOT block H0.6):
  (a) reuse an existing detached worktree if HEAD == source_sha and
      the tree is still clean (cheap; safe), or
  (b) give each build a unique worktree dir (e.g. include the
      build_config_hash and a timestamp).
```

## Notes for H0.5 second pass / H0.6 / H0.7

- The gate is what makes the evaluator trustworthy. The current gate is
  conservative (GGUF size as lower bound for VRAM, 10 % minimum free).
  An H0.5 second pass can tighten the bound by querying the model's
  actual peak VRAM via a warmup probe (load-and-measure).
- The decision rule treats every metric independently. A second pass
  should add a weighted product metric ("correct work per wall-hour")
  that outranks raw tok/s; until then the user-facing decision is
  per-metric, which is honest but noisy.
- The CLI has a BLOCKED-experiment path: when the gate fails the
  experiment row + a `blocked=True` run row are written so the operator
  sees the attempt in `list`. This is the right behaviour (auditability)
  and should be preserved across the H0.5 → H0.6 transition.
- The fork's `feature/rdna-llamacpp` branch has 8 commits (H0.0 +
  H0.0+ closure + H0.5 framework); all pushed to
  github.com/richardoros/Hyperloom.
